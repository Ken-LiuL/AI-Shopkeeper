# 美团竞品数据 RPC 设备采集方案

> 版本：v1.0 | 日期：2026-02-12
> 前置研究：[meituan-data-research.md](./meituan-data-research.md)

## 1. 方案概述

### 为什么需要 RPC 设备方案

美团竞品数据（周边竞品店铺、竞品商品排行、搜索关键词热度）**无法通过 Web 端获取**：

- **商家后台（牵牛花/经营宝）**：仅提供自有店铺数据，竞对分析维度有限且不可导出
- **H5 接口逆向**：mtgsig 3.0 签名算法极难逆向，维护成本极高
- **第三方数据服务**：美团即时零售领域无类似蝉妈妈的第三方平台
- **Playwright Web 自动化**：H5 页面反爬严格，浏览器指纹检测容易触发验证码

**移动端方案的优势**：
- 美团 App 原生环境，签名由 App 自动生成，无需逆向 mtgsig
- API 响应包含完整的结构化数据（比 DOM 解析可靠）
- 可通过 mitmproxy 透明拦截，无需修改 App
- Android 虚拟机可批量部署，支持多账号并行

## 3. 方案对比

### 方案 A：Frida RPC 方案

**原理**：Frida 注入美团 App 进程，Hook Java/Native 方法，直接拦截 API 请求/响应。

| 维度 | 评估 |
|------|------|
| 数据质量 | ⭐⭐⭐⭐⭐ 直接拿到内存中的解密数据 |
| 实现难度 | ⭐⭐ 需要逆向 App 找到 Hook 点 |
| 稳定性 | ⭐⭐ App 更新可能导致 Hook 点失效 |
| 反检测风险 | ⭐ 美团有 Frida 检测（ptrace、maps 扫描） |
| 维护成本 | 高 — 每次 App 更新需重新定位 Hook 点 |

**优势**：直接获取解密后的 API 响应，无需处理 SSL Pinning
**劣势**：美团对 Frida 有主动检测，需要额外的反反检测手段（魔改 Frida Server）

### 方案 B：adb + uiautomator2 + mitmproxy（推荐 ✅）

**原理**：通过 uiautomator2 控制 UI 操作，mitmproxy 作为系统代理拦截 HTTPS 流量。

| 维度 | 评估 |
|------|------|
| 数据质量 | ⭐⭐⭐⭐ API 响应的完整 JSON |
| 实现难度 | ⭐⭐⭐⭐ 相对简单 |
| 稳定性 | ⭐⭐⭐⭐ UI 变化不影响数据拦截 |
| 反检测风险 | ⭐⭐⭐⭐ 真实 App 操作，无注入行为 |
| 维护成本 | 低 — UI 选择器变化只需微调 |

**优势**：
- 不修改 App 进程，反检测风险最低
- mitmproxy 拦截的 API 响应是结构化 JSON，解析简单
- 即使 UI 变化导致自动化失败，mitmproxy 仍能工作
- 成熟的生态（u2 + mitm 都有活跃社区）

**劣势**：
- 需要安装 mitmproxy CA 证书（Android 7+ 需系统级证书）
- 部分 API 可能有 SSL Pinning（需用 JustTrustMe 等模块绕过）
- 操作速度受 UI 渲染限制

### 方案 C：Appium 方案

**原理**：通过 Appium Server 提供跨平台自动化，底层仍调用 uiautomator2。

| 维度 | 评估 |
|------|------|
| 数据质量 | ⭐⭐⭐⭐ 同方案 B（配合 mitmproxy） |
| 实现难度 | ⭐⭐⭐ 多一层 Appium 抽象 |
| 稳定性 | ⭐⭐⭐ Appium Server 偶有连接问题 |
| 反检测风险 | ⭐⭐⭐⭐ 同方案 B |
| 维护成本 | 中 — Appium 版本兼容性问题 |

**优势**：标准化的 WebDriver 协议，未来可扩展到 iOS
**劣势**：比直接使用 u2 多一层封装，增加复杂度和故障点

## 4. 推荐方案

### 🏆 方案 B：adb + uiautomator2 + mitmproxy

**理由**：
1. **反检测风险最低**：不注入 App 进程，不修改 APK，从外部观察和操控
2. **实现最简单**：u2 的 Python API 直观易用，mitmproxy 的 addon 模式强大灵活
3. **数据可靠**：直接拦截 API 响应 JSON，不依赖 DOM/UI 元素解析
4. **维护成本低**：UI 选择器和 API 域名是两个独立变量，单一变化不会完全失效
5. **生态成熟**：u2 和 mitmproxy 都有活跃的中文社区和文档

## 6. 安全风险评估

### 6.1 反检测措施

| 风险 | 对策 |
|------|------|
| 设备指纹检测 | 使用不同虚拟机实例，定期重置设备 ID |
| 操作频率异常 | 随机延迟 2-8 秒，模拟真人操作节奏 |
| 滑动轨迹检测 | 贝塞尔曲线模拟自然滑动轨迹 |
| 账号关联 | 多账号轮换，每账号每日限制操作次数 |
| IP 关联 | 使用不同代理 IP（住宅代理优先） |
| Root 检测 | 使用 Magisk Hide 隐藏 Root 状态 |
| mitmproxy 检测 | JustTrustMe/TrustMeAlready 绕过 SSL Pinning |

### 6.2 账号风控

- **账号池**：准备 3-5 个美团账号，手机号注册
- **轮换策略**：每个账号每日最多使用 2 次，间隔 4+ 小时
- **冷却期**：账号触发验证码后冷却 24 小时
- **养号**：新账号先正常使用 7 天再用于采集

### 6.3 法律合规

- 仅采集 C 端公开展示数据
- 不破解/修改 App（mitmproxy 是网络层操作）
- 频率控制在合理范围（每日 2-3 次）
- 数据仅用于自身经营决策，不转售
- 不存储用户个人信息

## 7. 数据采集频率建议

| 数据类型 | 频率 | 时段 | 说明 |
|---------|------|------|------|
| 搜索关键词排行 | 每日 2 次 | 10:00, 20:00 | 覆盖日间和晚间高峰 |
| 竞品店铺信息 | 每日 1 次 | 06:00 | 早间低峰期采集 |
| 竞品商品列表 | 每日 1 次 | 14:00 | 午间采集 |
| 品类热门排行 | 每周 3 次 | 周一/三/五 09:00 | 变化较慢 |

**单次采集预估时长**：
- 搜索 18 个关键词 × 30 秒/词 ≈ 9 分钟
- 5 家竞品店铺详情 × 60 秒/店 ≈ 5 分钟
- 总计单轮 ≈ 15 分钟

## 8. 目录结构

```
src/rpc/
├── __init__.py           # 模块导出
├── device_manager.py     # Android 设备管理（ADB、虚拟机）
├── meituan_client.py     # 美团 App 自动化（u2 + 反检测）
├── data_extractor.py     # API 响应解析 → DB 存储
├── proxy.py              # mitmproxy addon（HTTPS 拦截）
└── scheduler.py          # 采集调度（定时、轮换、重试）
```

## 9. 环境要求

- Python 3.10+
- Android SDK（ADB）
- Android 虚拟机（推荐 Android 10/11）：
  - 雷电模拟器 / 夜神模拟器（Windows）
  - Genymotion（macOS/Linux）
  - 或真机
- mitmproxy 10+
- uiautomator2
- Magisk（Root + Hide）
- JustTrustMe（SSL Pinning 绕过）
